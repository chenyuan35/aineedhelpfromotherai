# Product Value Gate

Status: mandatory pre-build and portfolio-review rule.

The project must not treat search volume, indexing, ranking, visual polish, or official documentation coverage as proof that a product is worth building.

Before any new tool, major expansion, or winner-optimization task, answer this first:

> Why can the user not solve this adequately by reading the official page, remembering a fixed date/rule, or doing one ordinary search?

If the answer is weak, stop. Do not build or deepen the product merely because the query has search volume.

Then answer a second hard question:

> Why should the user use us instead of the best existing independent product already solving the same job?

If a mature independent site already provides the same monitoring, history, calculation, workflow, freshness and usability at equal or better quality, stop unless we have a concrete differentiated advantage. A keyword opportunity is not a product opportunity when the job is already well served.

A product must provide at least one durable advantage that is materially useful to the user:

- information asymmetry: useful facts/signals are scattered, hard to find, or not available from the official source;
- prediction/uncertainty reduction: the outcome or timing is not fixed and the site can make a better evidence-backed estimate;
- aggregation: multiple independent sources must be reconciled to reach a useful answer;
- monitoring/freshness: the user benefits from not repeatedly checking changing sources themselves;
- computation/transformation: the site turns inputs into an answer that is meaningfully harder than reading a static rule;
- proprietary history: accumulated snapshots/outcomes materially improve the answer;
- decision-cost reduction: the site combines real alternatives, trade-offs, current outcomes, and actions in a way a single official source cannot;
- differentiated execution: an existing independent competitor may solve the broad job, but we solve a narrower high-value subproblem materially better.

Hard reject conditions:

- the core answer is deterministic, stable, obvious, and already shown clearly by the provider;
- the page mostly republishes or reformats official rules without adding independent evidence, prediction, aggregation, monitoring, computation, history, or decision value;
- the same user job is already solved well by mature independent products and we cannot name a concrete advantage;
- search demand is the main reason to build it;
- the page's value disappears once the user reads the official documentation once;
- the page's value disappears once the user discovers the strongest existing independent tool.

Source-role rule:

Official sources are authoritative for official facts: price, published limits, plan terms, reset rules, API behavior, product availability, and other provider-controlled facts. They are not automatically the product value.

For products whose value depends on real-world behavior, uncertainty, reliability, workarounds, operational outcomes, or hidden routes, prioritize independent user/community evidence, historical observations, and multiple current signals. Official pages are one input, not the whole answer.

Competition-role rule:

Before implementation, search the live market for the strongest independent products solving the same user job. Record what they already provide. Do not build a clone with a different domain name. A candidate advances only when the project can state a specific user-visible advantage that survives comparison with the best incumbent.

Reset-family rule:

A deterministic monthly/weekly reset that is plainly visible to the user is low-value by default. It should not be promoted merely because it has search volume. Reset Radar should prioritize cases where timing, availability, exceptions, banked resets, temporary policy changes, recovery behavior, quota loss or diagnostic ambiguity are uncertain and where external signals/history can reduce that uncertainty.

Codex-specific competition rule:

Codex reset demand is real, but generic reset-radar/history/countdown functionality is already served by multiple current independent sites. Do not build a generic Codex tracker. Any future Codex work must prove a narrower gap that current trackers do not already solve well.

Phone Radar rule:

Carrier/operator pages remain commercial metadata sources by default. Operational reality must continue to come from current independent user/community outcomes and route history.

Portfolio review rule:

Existing pages are not grandfathered in. If a page fails this gate, do not keep investing because development work has already been spent. Classify it as one of:

- KEEP / DIFFERENTIATE — clear non-official and non-commodity value exists;
- DOWNGRADE — retain the URL but stop promoting/investing until a stronger value proposition exists;
- REPURPOSE — preserve useful search equity but change the user job toward a defensible value;
- RETIRE — only after separate evidence/SEO/redirect review; never delete impulsively.

Mandatory review questions:

1. What uncertainty, hidden information, repeated checking, calculation, or decision burden does this page remove?
2. What can this page tell/do that the provider's own page cannot?
3. What can this page tell/do that the strongest independent competitor does not already do as well?
4. Which independent evidence or accumulated data supports that advantage?
5. Would a user have a reason to return?
6. If the official page became perfectly clear and fast tomorrow, would this product still have value?
7. If the best independent competitor were one click away, would this product still have a reason to exist?

If #2, #3, #6 or #7 cannot be answered convincingly, stop product expansion and re-evaluate the page.
